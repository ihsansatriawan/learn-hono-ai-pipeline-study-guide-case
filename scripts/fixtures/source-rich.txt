Lecture transcript: The Event Loop and JavaScript's Concurrency Model

Right, today we look at why JavaScript is called single-threaded and yet still manages
to handle many pieces of work at once. The key is not threads, it is the way the
runtime organises its queues of work.

First, the call stack. Every time a function is called, the runtime pushes a new frame
onto the stack. When the function returns, that frame is popped off. Because there is
only one stack, only one piece of code is ever truly running at any moment. That is what
single-threaded means. The consequence matters: if some function computes for five
seconds, the entire page freezes for those five seconds, animations and button clicks
included. We call that blocking.

Second, the Web APIs, or host APIs. Operations such as setTimeout, network requests, and
file reads are not performed by the JavaScript engine itself. They are handed off to the
host environment — the browser or Node.js — which does the work outside the call stack.
The moment the work is handed off, the call stack is empty again and free to move on to
the next thing. That is why setTimeout blocks nothing.

Third, the task queue, often called the callback queue or the macrotask queue. When a
host API finishes, its callback is not run immediately. It is queued. This queue is
first-in-first-out.

Fourth, the event loop itself. The event loop is a simple repetition that keeps checking
one thing: is the call stack empty? If it is, take one item off the queue and push it
onto the call stack. If it is not, wait. That is all. This is why even setTimeout with a
delay of zero does not mean "run now" — it means "run once the call stack is empty and
your turn arrives".

Fifth, the microtask queue. Promises do not use the ordinary task queue; .then callbacks
and await resumptions go into the microtask queue, which has higher priority. Each time
the call stack empties, the event loop drains the ENTIRE microtask queue first, and only
then takes a single macrotask. The practical upshot: an already-settled promise runs
before a zero-second setTimeout that was registered earlier. And if microtasks keep
scheduling new microtasks, macrotasks never get a turn — starvation.

So when you run into a stuttering UI, the first question is always the same: what heavy
piece of work is occupying the call stack, and can it be broken up or moved to a worker?
