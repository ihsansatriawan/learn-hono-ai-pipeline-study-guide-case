Transkrip kuliah: Event Loop dan Model Konkurensi JavaScript

Baik, hari ini kita bahas kenapa JavaScript disebut single-threaded tapi tetap bisa
menangani banyak pekerjaan sekaligus. Kuncinya bukan pada thread, melainkan pada cara
runtime mengatur antrean pekerjaan.

Pertama, call stack. Setiap kali sebuah fungsi dipanggil, runtime mendorong frame baru
ke atas tumpukan. Ketika fungsi selesai, frame itu dilepas. Karena tumpukannya cuma
satu, hanya ada satu potong kode yang benar-benar berjalan pada satu waktu. Inilah arti
single-threaded. Konsekuensinya penting: kalau ada fungsi yang menghitung sesuatu selama
lima detik, seluruh halaman membeku selama lima detik itu, termasuk animasi dan klik
tombol. Kita menyebutnya blocking.

Kedua, Web API atau host API. Operasi seperti setTimeout, permintaan jaringan, dan
pembacaan berkas tidak dikerjakan oleh mesin JavaScript sendiri. Mereka diserahkan ke
lingkungan host — browser atau Node.js — yang mengerjakannya di luar call stack. Begitu
diserahkan, call stack langsung kosong lagi dan bisa mengerjakan hal berikutnya. Inilah
sebabnya setTimeout tidak memblokir apa pun.

Ketiga, task queue, sering disebut callback queue atau macrotask queue. Ketika host API
selesai, callback-nya tidak langsung dijalankan. Ia diantrekan. Antrean ini bersifat
first-in-first-out.

Keempat, event loop itu sendiri. Event loop adalah pengulangan sederhana yang terus
memeriksa satu hal: apakah call stack kosong? Kalau kosong, ambil satu item dari antrean
dan dorong ke call stack. Kalau tidak kosong, tunggu. Itu saja. Karena itu setTimeout
dengan delay nol pun tidak berarti "jalankan sekarang" — artinya "jalankan setelah call
stack kosong dan giliranmu tiba".

Kelima, microtask queue. Promise tidak memakai task queue biasa; callback .then dan
await masuk ke microtask queue yang punya prioritas lebih tinggi. Setelah setiap kali
call stack kosong, event loop menguras SELURUH microtask queue dulu, baru mengambil satu
macrotask. Akibat praktisnya: promise yang sudah selesai akan dijalankan sebelum
setTimeout nol detik yang didaftarkan lebih dulu. Dan kalau microtask terus-menerus
menjadwalkan microtask baru, macrotask tidak pernah kebagian giliran — starvation.

Jadi kalau kalian menemukan UI yang tersendat, pertanyaan pertamanya selalu sama: ada
pekerjaan berat apa yang sedang menduduki call stack, dan bisakah ia dipecah atau
dipindahkan ke worker?
